# YoPay API

Base URL: `https://api.yopay.com.bd`. Every `/v1` call is signed. JSON in, JSON out.

## Signing a request

Four headers:

```
X-YoPay-Key:       k_live_...
X-YoPay-Timestamp: 1790269500        seconds since the epoch
X-YoPay-Nonce:     a random string, never repeated
X-YoPay-Signature: hex HMAC-SHA256 (case does not matter)
```

The signature covers this exact string, newline separated:

```
POST
/v1/payment/create
1790269500
n-abc-123
234BC9DF...                           SHA-256 of the raw body, hex
```

Method and path are in there for a reason: without the method a signed `GET` replays as a
`DELETE`, and without the path a signature for one invoice authorises another. The body is
hashed rather than concatenated so the shape stays fixed whatever the body is.

The nonce must be new each time. The server remembers the ones it has seen and refuses a
repeat — that, not the five-minute clock window, is what stops a captured request being
sent twice. Clocks may differ by up to five minutes.

A request with a body that is not signed, or is signed with the wrong secret, gets `401`
with a body that says only `unauthorized`. It never says which of the two was wrong,
because that would tell an attacker which key ids exist.

Rate limit: 120 requests a minute per key, then `429`.

## Payments

### `POST /v1/payment/create`

```json
{ "orderRef": "ORD-1041", "amount": 500.00, "method": "Bkash" }
```

Optional: `walletId`, `customerName`, `customerEmail`, `customerMsisdn`, `redirectUrl`,
`metadataJson`.

`201` with the invoice, or `200` with the invoice that already existed for that
`orderRef`. **Repeating a create is safe and is the intended way to handle a retry.**

```json
{
  "invoiceId": "0192...",
  "orderRef": "ORD-1041",
  "amount": 500.00,
  "chargedAmount": 500.00,
  "currency": "BDT",
  "status": "AwaitingPayment",
  "expiresAt": "2026-09-25T10:25:00+00:00",
  "checkoutUrl": "https://pay.yopay.com.bd/pay/0192..."
}
```

Show **`chargedAmount`**, never `amount`. YoPay may adjust the figure by a few poisha so
that the incoming amount is unambiguous on that wallet; `chargedAmount` is what the
customer must actually send, and telling them anything else means the payment will not
match.

`409` means the merchant has no wallet for that method.

### `POST /v1/payment/verify`

```json
{ "orderRef": "ORD-1041" }
```

or `{ "invoiceId": "0192..." }`. Answers `200`:

```json
{ "invoiceId": "0192...", "status": "Paid", "receivedAmount": 500.00, "paidAt": "..." }
```

**Call this before fulfilling an order, even after a webhook says the invoice is paid.**
The webhook tells you to look; this is the record.

### `GET /v1/payment/{invoiceId}`

The full invoice, same shape as create. `404` if it is not yours — not `403`, so the
answer cannot be used to discover which invoice ids exist.

### `POST /v1/payment/cancel`

```json
{ "orderRef": "ORD-1041" }
```

`200` with the cancelled invoice. Cancelling something already cancelled is also `200`.
`409` if it has been paid — cancelling would not return the money; refund the customer.

Worth calling on an abandoned cart: every open invoice reserves one amount on the wallet.

## Webhook endpoints

### `POST /v1/webhooks/endpoints`

```json
{ "url": "https://shop.example.com/yopay" }
```

`201`, and **this response is the only place the signing secret ever appears**:

```json
{ "endpointId": "0192...", "url": "...", "state": "Valid", "isActive": true,
  "secret": "base64..." }
```

Store it before doing anything else. Nothing can show it again; a merchant who loses it
registers the endpoint afresh.

`https://` only, port 443 or 8443, resolving to a public address. `400` otherwise, with
the reason.

### `GET /v1/webhooks/endpoints`

Every endpoint, without secrets.

### `DELETE /v1/webhooks/endpoints/{id}`

`204`. Deactivated rather than deleted, so old deliveries still show where they were sent.

## Statuses

`Created`, `AwaitingPayment`, `Partial`, `PendingReview`, `Paid`, `Settled`, `Expired`,
`Cancelled`.

`PendingReview` means the window elapsed with nothing matched. It is not a failure —
provider messages run minutes late and an offline handset uploads hours late, so an
invoice waits there rather than failing outright.

## Errors

`application/problem+json`, with `title` in plain language. `400` malformed, `401`
signature, `404` not yours or not there, `409` the state forbids it, `429` rate limit.

A call that never gets an answer at all is the case worth thinking about: the request may
well have arrived and been acted on. Retry it — `create` and `cancel` are both idempotent,
which is what makes that safe.

## SDK

`sdk/php` — no dependencies, PHP 8.1+. See its README. Porting to another language: check
against `sdk/php/tests/vectors.json`, which is generated by the server, rather than
against your reading of this page.
